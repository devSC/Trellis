# Behavior Equivalence Matrix — design-grill

> Scope: Stage A evidence. This matrix is derived from the four legacy grill skills:
> `client-grill`, `go-design-grill`, `h5-design-grill`, and `ios-design-grill`.
> It defines what the new `design-grill` must preserve behaviorally without
> inlining platform-specific doc_type or SLOT tokens in the skill body.

## Shared Behavior Contract

| Capability | Required equivalent behavior in `design-grill` |
| --- | --- |
| Runtime position | Run before the requirements Gate for `prd.md` and before the overview Gate for `design.md` / `design-main.md`; do not replace brainstorm, writing, review, or implementation check skills. |
| Question style | Grill one branch at a time; ask exactly one question per turn; include a recommended answer and evidence basis; wait for user feedback before continuing. |
| Evidence discipline | If code or spec can answer the question, read it first and cite the local evidence instead of asking the user. |
| Decision persistence | Persist decisions immediately into the owning artifact: behavior/scope/failure path to `prd.md`; ownership/doc_type/three-question rationale to `design.md` or `design-main.md`; terminology to `CONTEXT.md`; hard-to-reverse tradeoffs to ADR. |
| Terminology pressure | Challenge overloaded or conflicting terms against `CONTEXT.md`; record final language and flagged ambiguity. |
| Boundary pressure | Invent edge scenarios to force a unique owner, failure closure, concurrency/write-owner rule, and cross-layer dependency direction. |
| Project conventions | Treat `project-conventions.md` as the only effective project-level source. Template/sample files are not ready state. Project-level slot changes require user confirmation plus ADR/conventions revision; the grill must not silently edit project conventions. |
| Redline handling | Preserve the thick-skill behavior: if a runtime summary shows a platform hard redline is touched, immediately fail the grill branch, report the redline, evidence anchor, and upstream rollback target, then stop until the artifact is corrected. |
| ADR gate | Propose ADR only when all three conditions hold: hard to reverse, surprising without context, and a real tradeoff. |
| Output language | Chinese first for user-facing questions and conclusions; keep identifiers, commands, paths, protocol fields, and library names in their original spelling. |

## Non-Equivalence Risks To Avoid

- Do not collapse redline fail into generic "ask more questions"; old go/h5/iOS skills stop and require rollback when hard redlines are touched.
- Do not treat `project-conventions.template.md` or sample convention files as usable project conventions.
- Do not "read every possible source" when authority is specified. For Go/H5, doc_type comes from overview SSOT; for iOS, it comes from conventions index §5. Conflicts must fail closed.
- Do not remove platform cue quality. The generic skill may avoid hardcoded platform token lists in its body, but it must force a runtime "grill checklist summary" containing the platform's redlines, boundary probes, code anchors, and ADR archetypes before questioning.
- Do not turn the skill into a Gate verdict. It is a pre-review grill: it rewrites artifacts and can fail/rollback a grill branch, but formal Gate pass/fail still belongs to the corresponding review/gate path.
