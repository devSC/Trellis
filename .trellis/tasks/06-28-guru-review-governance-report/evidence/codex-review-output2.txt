# Review Checklist

Use this checklist to perform a strict completeness review. The checklist exists to reduce false confidence and prevent hidden gaps from being smoothed over.

## 0. Current-code alignment
When code, diffs, repository snippets, tests, configs, schemas, or deployment scripts are available, check the plan against the actual implementation.

Check whether the review has enough code context to answer:
- which files or modules will be touched
- which current behaviors already exist
- which interfaces, models, or utilities are shared
- which tests already cover the behavior
- which release or migration paths already constrain the change

Common gaps:
- reviews the plan as if the system were greenfield
- accepts the plan's description of the current system without checking code
- misses shared code paths, compatibility branches, or hidden coupling
- ignores current tests, feature flags, config switches, migrations, or deployment scripts
- treats a wide-impact change as a local change

Severity guidance:
- severe: the plan conflicts with current code reality or ignores a broad blast radius visible in code
- medium: some relevant implementation areas are checked, but important code paths are not reviewed
- minor: the main code paths are covered, but some supporting files could still be checked

If you find a gap here, also state the default recommended remediation and explain why it best fits the current code reality.
When code context exists and the user explicitly allows delegation, ensure a subagent completed the first-pass code reconnaissance before the final review is synthesized. If delegation is not explicitly authorized, ensure the main agent completed the same reconnaissance locally.

## 1. Goal and success criteria
Check whether the plan clearly states:
- what problem is being solved
- what outcome is expected
- how success will be measured
- what counts as done

Common gaps:
- only describes actions, not outcome
- uses vague goals such as "optimize" or "improve" without metrics
- has no clear acceptance condition

Severity guidance:
- severe: no clear goal or no way to verify success
- medium: goal exists but success criteria are incomplete or partially subjective
- minor: wording is understandable but not crisp enough

If you find a gap here, also explain how to rewrite the goal or success criteria in the most direct and verifiable way for this context.

## 2. Scope and non-goals
Check whether the plan defines:
- what is included
- what is excluded
- which edge cases are intentionally not covered

Common gaps:
- no non-goals section
- no boundary between phase 1 and later phases
- unclear edge-case coverage
- the scope ignores code paths that obviously share the same implementation

Severity guidance:
- severe: scope ambiguity can cause major rework or uncontrolled expansion
- medium: boundaries exist but are incomplete
- minor: sequence or naming is slightly unclear

If you find a gap here, also recommend the cleanest scope boundary or non-goal statement that reduces rework risk.

## 3. Assumptions and preconditions
Check whether the plan makes hidden assumptions about:
- upstream data or APIs
- permissions or approvals
- staffing or team support
- environment readiness
- legal, privacy, or compliance constraints
- current code structure being simpler or more isolated than it really is

Common gaps:
- assumes external support without commitment
- assumes data quality or API stability without stating it
- assumes required access already exists
- assumes refactor impact is limited without checking call sites and shared utilities

Severity guidance:

# Plan Reviewer

## Overview

Review plans in Chinese and focus on finding concrete problems first, then converging each valid finding to a context-grounded best remediation. Support four common plan types: development plans, technical designs, product implementation plans, and general project plans. Treat the user's text as potentially incomplete unless the plan explicitly covers key execution details. When the current implementation is available, review the plan against the code rather than against abstract best practices alone.

## Workflow

Follow this sequence every time:

1. Classify the plan type and extract the stated goal, scope, assumptions, dependencies, milestones, validation approach, and release or operation details.
2. Check whether current implementation context is available, such as code files, diffs, repository snippets, interfaces, tests, configs, schemas, or deployment scripts.
3. If the user explicitly allows delegation or subagent use, you may use one or more subagents to perform reconnaissance on the plan text, code alignment, call chains, state semantics, tests, release paths, or missing context.
4. If code is available, inspect it carefully and ground the review in the actual implementation. When the user explicitly allows delegation, prefer a subagent for the first-pass implementation reconnaissance; otherwise the main agent must do the same reconnaissance locally.
5. If the change is flow-driven, stateful, asynchronous, event-driven, timer-driven, stream-driven, cache-driven, or involves retries/batching/fallbacks, perform a dedicated method-order audit. When the user explicitly allows delegation, a subagent may do that first pass; otherwise the main agent must do it locally.
6. Audit the plan against the review checklist in `references/review-checklist.md`.
7. Mark missing or unclear information as gaps instead of inventing details.
8. After the subagent returns, the main agent must converge on one default recommended remediation for each valid finding that fits the current implementation, blast radius, compatibility constraints, validation path, and delivery cost.
9. Rank findings by severity: severe, medium, minor.
10. If the finding is flow-driven, stateful, asynchronous, event-driven, timer-driven, stream-driven, cache-driven, or involves retries/batching/fallbacks, prepare concise sequence diagrams for both the current problem path and the recommended path.
11. Output the review in Chinese using the fixed structure below.

## Core rules

- Default to strict review mode. Do not begin with praise such as "整体不错" or "基本合理" unless the plan truly has no meaningful issues.
- Do not rewrite or optimize the whole plan unless the user explicitly asks for a revised version in a later turn.
- Do not treat implied assumptions as confirmed facts.
- If a required element is absent, call it missing explicitly.
- Prefer concrete critique over generic advice. Name the exact missing item, ambiguity, contradiction, or risk.
- When the user provides little context, say what information is missing and explain why the missing information matters.
- Keep the output findings-first. The main output is a problem list with best remediations, not a polished replacement plan.
- When the user explicitly allows delegation, prefer using a subagent for reconnaissance; when delegation is not explicitly authorized or subagent use is unavailable, the main agent must complete the same review locally.
- If a subagent is used, it is responsible for reconnaissance; the main agent is responsible for synthesis and final judgment.
- For every valid finding, provide one default recommended best remediation instead of stopping at critique alone.
- A best remediation must be grounded in current context, implementation constraints, blast radius, verification cost, and rollout reality.
- If multiple solutions exist, recommend one default option and explain why it is better than the alternatives in the current context.
- If context is insufficient to prove a single optimal solution, say what is missing and give the safest conditional default recommendation instead of pretending certainty.
- When the user only asks to review, do not directly replace the original plan with a fully rewritten version.
- When current code or repository context is available, do not review the plan in isolation. Verify the plan against the actual implementation before judging completeness.
- When code is available, explicitly check whether the plan matches the current code paths, interfaces, constraints, naming, data flow, test coverage, and release mechanism.
- In code-backed reviews, a subagent may do the first-pass implementation reconnaissance only when the user explicitly allows delegation; otherwise the main agent must do it locally before deciding severity and remediation.
- Do not assume the plan's description of the current system is correct. Confirm it from the code when possible.
- If the plan says a change is small, low-risk, compatible, or localized, verify that claim from the current implementation instead of repeating it.
- If code evidence is incomplete, state which files or areas are still missing from review.
- If the change involves streams, observers, timers, caches, snapshots, retry loops, batching, status machines, or multi-step method chains, you MUST explicitly inspect edge cases for those mechanisms instead of stopping at high-level completeness.
- Do not stop after “the main path looks right”. You must also ask whether repeated success, partial success, empty input, stale cache, duplicate invocation, timer re-entry, snapshot semantics, and fallback-path semantics are decision-complete.

## Code-grounded review

When implementation context is available, add this lens to every review:

- Map each major planned change to the current code location it would affect.
- Inspect the relevant code carefully, ideally line by line for short snippets and narrowly scoped files.
- Check whether the plan missed touched call sites, shared utilities, configs, schema definitions, tests, migrations, and deployment logic.
- Look for hidden coupling, duplicated logic, feature flags, fallback branches, legacy compatibility paths, and assumptions that are contradicted by code.
- Compare the plan's stated impact with the real blast radius implied by imports, call chains, data contracts, and runtime behavior.
- Check whether the plan's testing and rollout approach is consistent with the current test suite and release mechanism.
- If the plan proposes refactoring or replacement, check whether current code has side effects or edge cases that the plan did not mention.
- When code is available, the recommended remediation should explicitly reflect those code realities instead of falling back to generic architecture advice.

## Subagent execution

Use a delegation-aware split:

- If the user explicitly allows delegation, the subagent performs reconnaissance first and the main agent synthesizes the final Chinese review.
- If delegation is not explicitly authorized or subagent use is unavailable, the main agent performs the reconnaissance locally and still synthesizes the final Chinese review.

Subagent responsibilities when used:

- Extract plan structure, goals, scope, assumptions, dependencies, milestones, and missing sections
- Inspect code alignment when repository context is available
- Reconstruct key call chains, state transitions, and flow-heavy runtime order when needed
- Identify missing code areas, missing context, or blind spots that limit confidence

Main-agent responsibilities:

- Decide severity and section placement
- Converge on the default recommended remediation
- Write the plain-language explanations
- Decide which items belong in `待确认问题`
- Produce sequence diagrams and the final numbered card-style output

Do not let the subagent directly become the final review. The main agent must digest, reconcile, and rewrite the final answer. If no subagent is allowed, the main agent must still complete the same reasoning path and, when relevant, say what constraints limited delegation.

### Method-Order Review (mandatory for flow-heavy changes)

When the plan touches any chain like observer -> report -> query -> settle, or timer -> refresh -> retry, or stream -> cache -> snapshot, do a dedicated method-order review:

- Reconstruct the runtime sequence step by step in actual call order
- For each step, ask what input it consumes, what output it mutates, and what later steps depend on it
- Check whether the plan defines:
  - repeated-success semantics
  - partial-success semantics
  - empty-input semantics
  - stale-cache / retained-state semantics
  - duplicate invocation protection
  - current snapshot semantics versus stream semantics
  - timer/retry/fallback re-entry behavior
- Call out any place where the plan says “do X” but does not define what happens to already-cached state, subsequent calls, or downstream readers
- For every gap you find in this pass, state the recommended semantics and why they are the best fit for the current flow.
- Default to adding both a concise "问题时序图" and a concise "最优解时序图" for these findings. Prefer Mermaid `sequenceDiagram` when it helps readability.

If this method-order pass is not done for a flow-heavy change, the review is incomplete.

## Review dimensions

Always inspect these dimensions. Adapt wording to the plan type, but do not skip them silently:

- Goal clarity and success criteria
- Scope and non-goals
- Preconditions and hidden assumptions
- Dependencies, ownership, permissions, and resources
- Alignment with the current code implementation
- End-to-end flow completeness, including exceptions and fallback paths
- Execution order, milestones, and deliverables
- Verification, testing, and acceptance criteria
- Release, rollback, monitoring, documentation, and handoff
- Internal consistency across target, timeline, staffing, technical choices, and current code reality
- Method-order and edge-case completeness for stateful or asynchronous flows

For detailed prompts and severity guidance, read `references/review-checklist.md`.

Use a title-style card layout for each finding. Number entries within their section as `1. 2. 3.` and reset numbering per section.
Each finding must have exactly one numbered title line, followed by plain field lines.
For each issue, prefer this pattern:

1. 问题：<简短标题>

问题：<what is wrong, missing, or inconsistent with code>
原因：<why it is a problem>
后果：<what can go wrong>
最优解：<the default recommended fix in the current context>
最优解理由：<why this option is better than the alternatives here>
通俗解释：<plain-language explanation for non-owners>

Keep wording concise but specific.

For flow-heavy or stateful code paths, additionally name:

触发点：在哪个方法 / 观察链 / timer / 重试分支出现
缺失语义：计划没有定义什么时序或状态规则

Use Mermaid `sequenceDiagram` when it improves readability. The diagrams should show trigger source, key methods, state reads or writes, failure point, and downstream impact. The recommended diagram should show the semantic or ordering change directly, not only a happy path.
Keep the title on its own line and list the fields below it as plain text lines. Do not number, bullet, or indent the fields underneath the title.

## Pending-question boundary

- Use severe / medium / minor findings for items that are already identifiable defects, omissions, contradictions, or code mismatches.
- Use `待确认问题` only for issues that still require a product, business, ownership, dependency, or runtime-semantics decision to be locked.
- Do not move a clear defect into `待确认问题` just because it can be phrased as a question.
- Even in `待确认问题`, always provide a default recommended answer rather than leaving the user with an unanchored decision.

## Plan-type adaptation

### Development plan
Pay extra attention to module boundaries, interfaces, data structures, compatibility, testing coverage, deployment, rollback, monitoring, and the actual call sites or shared utilities touched by the current code.

### Technical design
Pay extra attention to architectural assumptions, tradeoffs, non-functional requirements, failure handling, migration path, operational risk, and whether the current codebase supports the proposed design boundaries.

### Product implementation plan
Pay extra attention to requirement boundaries, cross-functional dependencies, acceptance criteria, metrics, release readiness, and the concrete application surfaces the code already exposes.

### General project plan
Pay extra attention to milestones, owners, sequencing, external dependencies, communication, risk response, and whether the current implementation implies hidden work the plan did not schedule.

    78	| INV-V2-GROUP-AUTHORITY | V2 nested group 一旦出现，同 source 的 flat fallback 不能补同类型 Cell | partial V2 group 缺 videoGroup 时，不得从 flat media 补 video Cell |
    79	| INV-LOCAL-FACTS-ONLY | local DB 只能补 status / liked / attempt / url 等 facts，不能决定当前 V2 Cell membership | remote V2 group 未返回的本地 item 不得 append 到 visible displayItems |
    80	| INV-CURRENT-SELECTION | group.current 决定 Cell 当前项 | selectedInGroup 不能被 fallback 或 local order 覆盖 |
    81	| INV-LEGACY-ISOLATION | 非 V2 legacy flat media 在混合页仍保留 | V2 source 屏蔽 flat fallback 时不能误删非 V2 source |
    82	
    83	### 3.2 根因二：review target 没有窄化
    84	
    85	如果一个 check 同时面对 API client、DTO、repository projection、DAO local merge、controller、widget tests 和 generated files，reviewer 很难系统证明每个 edge case。
    86	
    87	需要把 review target 改成：
    88	
    89	- `target_kind`: `slice | staged | commit | range`
    90	- `target_paths`: 文件清单
    91	- `slice_id`: 关联 trace slice；第一版直接使用现有 `UNIT-<slug>` 作为 join key，避免另引入 `SL-xx` 体系
    92	- `invariant_ids`: 本轮必须检查的不变量
    93	- `deterministic_checks`: 已运行命令与结果
    94	- `dirty_state`: 与本任务无关的 dirty paths
    95	
    96	### 3.3 根因三：implementation check 缺少独立对抗 review
    97	
    98	当前 adversarial 只覆盖 requirements / overview / detail。代码实现阶段最容易出现实际语义偏差，却没有相同等级的 opposite-provider review 机制。
    99	
   100	这不意味着必须启用 OCR。更合理的是把 implementation semantic review provider 抽象出来：
   101	
   102	- `manual`
   103	- `codex`
   104	- `claude`
   105	- `ocr_optional`
   106	
   107	高风险 slice 默认至少需要一个非实现者 review provider；OCR 不在默认必选集合。
   108	
   109	### 3.4 根因四：review record 不够结构化
   110	
   111	overview/detail 有 review_runs 和 digest；implementation check 主要依赖文本里的 `review_result=clean/final-verification-ready`。这不够支持审计：
   112	
   113	- 不知道审的是哪个 target；
   114	- 不知道覆盖了哪些 invariants；
   115	- 不知道哪些 deterministic checks 先通过；
   116	- 不知道剩余 P2 / follow-up / nice-to-have 是否被接受；
   117	- 不知道是否有 dirty diff 干扰。
   118	
   119	## 4. 解决方案
   120	
   121	### 4.1 原则
   122	
   123	1. OCR 不是硬依赖。OCR 只能作为 optional semantic review provider。
   124	2. deterministic checks 是 gating 目标。P0 由 worker 按 packet 中可复跑命令执行并自报，packet 命令是可复跑 SSOT；supervisor-side 真正硬 Gate 在 P1 落地。
   125	3. Guru review 的输入必须可判定。没有 slice packet / invariant matrix，不允许声称 clean。
   126	4. 上游合同缺失必须回退。实现中发现 detail 缺不变量，应输出 `DETAIL_DEFECT`，先补设计合同。
   127	5. dirty worktree 必须隔离。review target 之外的 staged / unstaged / untracked 必须显式列出并排除。
   128	
   129	### 4.2 新增 Slice Review Packet
   130	
   131	每个 high-risk implementation slice 在进入 semantic review 前必须生成一个机器可读 packet。
   132	
   133	唯一落地位置：
   134	
   135	```text
   136	<task_dir>/slice-packets/<unit_id>.json
   137	```
   138	
   139	生产者：
   140	
   141	- supervised 模式下，packet 是实现前输入合同：由主会话 / planning-writing 阶段基于 `implement.md` 与 detail contract 创建，必须在首次 `guru_supervise.py implement-check` 前已经存在；
   142	- `flutter-implementation-guru-writing` 在实现 high-risk slice 前读取并校验 packet，可补充 deterministic check 计划，但不承担首次创建 packet；
   143	- inline 模式由主 agent 在编辑前创建；
   144	- packet 文件名、`slice_id` 和 `owner_unit` 第一版都使用现有 `UNIT-<slug>`；`implement.md` 计划节必须列出同一个 UNIT 与 `slice_packet` 路径，作为 packet ↔ trace 的机器 join key。
   145	
   146	消费者：
   147	
   148	- `guru_supervise.py implement-check` 在 spawn implement / check worker 前读取 packet 并做 scope preflight；

   210	### 4.3 新增 Invariant Matrix
   211	
   212	Slice packet 的 `invariants[]` 是 invariant matrix 的唯一机器 SSOT；`implement.md` 和设计包只能引用或摘要，不再维护第二份机器矩阵。这样避免 gate 读 A、skill 读 B 时产生漂移。
   213	
   214	| invariant_id | source | owner | positive case | negative case | test evidence | route if missing |
   215	| --- | --- | --- | --- | --- | --- | --- |
   216	| INV-LOCAL-FACTS-ONLY | detail / requirement-api | DAO | remote item gets local facts | omitted remote V2 item stays stored but not displayed | datasource unit test | DETAIL_DEFECT |
   217	
   218	审查时必须逐条给出 `pass / fail / not_applicable`。packet schema 必填 `invariant_id`、`rule`、`source`、`owner`、`positive_case`、`negative_case`、`test_evidence`、`route_if_missing`；只给 invariant id 不合格，因为 reviewer 无法从 id 推断负向语义合同。
   219	`invariant_coverage` 聚合规则：任一 invariant 为 `fail` 则 `failed`；任一 high-risk invariant 没有证据且不能合理标为 `not_applicable` 则 `missing`；其余情况，包括部分 invariant 明确 `not_applicable` 且理由成立，聚合为 `all_passed`。
   220	这里的“证据”以审查期 reviewer 对实际测试、命令输出、代码路径和记录文件的判定为准；packet 创建期的 `test_evidence[]` 是计划指针，可以为空。实现后向某个 invariant 补充测试名、命令或证据文件属于允许的 evidence 补充，不改变 invariant 语义；不得在实现后改写 `rule`、`positive_case`、`negative_case`、`owner` 或 `route_if_missing` 来迁就实现。
   221	第一版中，high-risk invariant 定义为 `risk=high|critical` 的 slice packet 内全部 `invariants[]`；不额外引入 per-invariant criticality 字段，避免同一 packet 内多套风险口径。
   222	
   223	### 4.4 修改 Implementation Review 输出合同
   224	
   225	implementation check 不再只输出自由文本。worker 输出必须置顶：
   226	
   227	```text
   228	review_result=clean|findings|blocked
   229	route_class=none|IMPLEMENT_DEFECT|PROCESS_DEFECT|DETAIL_DEFECT|OVERVIEW_DEFECT|REQ_BLOCKER
   230	review_target=<slice|staged|commit|range>:<id>
   231	review_provider=<manual|codex|claude|ocr_optional>
   232	deterministic_checks=<passed|failed|missing>
   233	dirty_scope=<clean|isolated|invalid>
   234	invariant_coverage=<all_passed|failed|missing>
   235	```
   236	
   237	字段语义：
   238	
   239	- `review_result` 和 `route_class` 仍是 worker 输出的最小字段。
   240	- `review_result` 的 jsonl 规范值固定为 `clean|findings|blocked`。worker 兼容输入可以把 `final-verification-ready` 作为 `clean` 的同义裁决；`guru_review_record.py` 在写入前统一归一为 `review_result=clean`，manual CLI `--result clean` 直接使用同一规范值。
   241	- `review_target`、`review_provider`、`deterministic_checks`、`dirty_scope`、`invariant_coverage` 第一版作为 gating 字段解析；缺失任一字段时，check 不可 clean。
   242	- 取值级 gating：归一后的 `review_result=clean` 仅当 `deterministic_checks=passed`、`dirty_scope in {clean,isolated}`、`invariant_coverage=all_passed` 时可接受；任一字段存在但取非通过值却仍声明 clean，supervisor 按 `MALFORMED_REVIEW_OUTPUT` 拒绝并写入 jsonl，不接受为成功。
   243	- P0 中 `deterministic_checks` 由 worker 按 packet 命令执行并自报，packet 内命令是可复跑 SSOT；supervisor 可做廉价抽检但不作为 P0 必需项。若要把 deterministic checks 升级为真正 supervisor-side hard Gate，作为 P1 由 supervisor 在 preflight 后独立执行 packet.deterministic_checks 并比对结果。
   244	- `SCOPE_INVALID` 和 `MALFORMED_REVIEW_OUTPUT` 是 supervisor-only failure code，写入 `implementation-reviews.jsonl.supervisor_failure`，不属于 worker `route_class`，不要求扩展 worker `ROUTE_RE`，也不要求 worker 在置顶输出里打印 `supervisor_failure`。
   245	- worker 若输出 `clean` 但缺少新增 gating 字段，supervisor 记录 `review_result=blocked`、`route_class=none`、`supervisor_failure=MALFORMED_REVIEW_OUTPUT`、`repairable=false`，exit 2；不能把格式不合格的 clean 当作成功，也不能让 implement worker 空转修复审查格式。
   246	- supervisor 在每轮 check 后追加结构化记录到：
   247	
   248	```text
   249	<task_dir>/review-records/implementation-reviews.jsonl
   250	```
   251	
   252	每行包含 `run_id`、`slice_id`、`target_paths`、`review_provider`、`route_class`、`review_result`、`deterministic_checks`、`dirty_scope`、`invariant_coverage`、`channel`、`worker`、`timestamp`、`supervisor_failure`、`repairable`。`supervisor_failure` 正常 worker 轮次为 `none`，supervisor 硬停轮次填 `SCOPE_INVALID` 或 `MALFORMED_REVIEW_OUTPUT`；`repairable` 正常 worker finding 根据 `route_class` 判定，supervisor 硬停为 `false`。channel events 仍保留原始审查输出，jsonl 是任务内可审计索引。非 channel provider 仍写同一字段：manual 行固定 `channel=manual`、`worker=<reviewer>`；显式触发的 OCR 行固定 `channel=ocr_optional`、`worker=<tool-or-run-id>`。这些 sentinel 由 `guru_review_record.py append` 根据 `--provider`、`--reviewer`、`--run-id` 派生，不要求手工传 `--channel` / `--worker`。supervisor 与 manual / OCR append 都必须复用 `guru_review_record.py` 的共享 schema 校验与写入函数，避免一个 jsonl 两套 writer 漂移。取值级一致性拒绝也属于该共享校验：任何 provider 写入 clean 型裁决时，必须同时满足 `deterministic_checks=passed`、`dirty_scope in {clean,isolated}`、`invariant_coverage=all_passed`；否则由共享 writer 拒绝并记录 / 返回 `MALFORMED_REVIEW_OUTPUT`。该判定由 `guru_review_record.py` 暴露的单一共享校验函数承担，supervisor 的 parse-time route / exit gating 与 manual / OCR append 的 write-time gating 都调用它，不能在两侧各自实现。
   253

   437	## 7. 成功标准
   438	
   439	1. 对 Himora V2 local merge 这类问题，若 detail 已写 invariant，implementation check 必须能定位到具体 `IMPLEMENT_DEFECT`。
   440	2. 若 detail 未写 invariant，implementation check 必须输出 `DETAIL_DEFECT`，不能靠代码实现私自拍板。
   441	3. 无 OCR 的情况下，Claude / Codex / manual review provider 能完成语义审查闭环。
   442	4. OCR 可继续存在，但只作为 optional bounded provider。
   443	5. dirty worktree 下 review target 必须可审计，不能把 unrelated lockfile / generated churn 混进 clean 结论。
   444	6. scope-invalid 不会触发 3 次 implement repair 空转。
   445	7. packet 是 invariant matrix 的唯一机器 SSOT；不会出现 implement.md 与设计包矩阵漂移。
   446	8. `packages/cli/src/templates/guru/**` 的变更来自 sync 命令，不来自手工 patch；sync 后可审查生成镜像 diff，避免源模板与 CLI 内置模板漂移。
