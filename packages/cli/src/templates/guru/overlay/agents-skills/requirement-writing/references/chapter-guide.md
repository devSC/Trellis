# 需求文档分章写作指南

说明：文档组织与完成口径必须以同级标准包 `../requirement-doc-standard/references/requirement-structure-single-source.md` 为单一来源（从 requirement-writing Skill 目录解析）；由入口 `SKILL.md` 负责定位并读取标准包。本文仅给出分章写作与阶段推进细则。

## 目录
- 基本原则
- 文档承载约定（语义 SSOT）
- 双时态写作口径
- 核心能力收敛（在第一章 1.4 之后执行）
- 阶段切换与暂停
- 第一章：产品总述
- 第二章：入口组织结构（有 UI 时为页面组织结构）
- 第三章起：页面详细描述
- 服务端 API 定义（若适用）
- CLI Command 定义（若适用）
- 非功能需求
- 完成收敛清单

## 基本原则

始终遵守以下原则：
- 完整性：功能/场景清单要覆盖需求范围。
- 关键性：核心能力只保留重点/难点行为，不追求覆盖率。
- 清晰性：结构清楚、语言明确。
- 一致性：术语、入口名、页面名、组件名、API/CLI 名保持一致。
- 可追踪性：入口、流程、API/CLI、非功能要求能互相对应。
- 可测试性：触发条件、输入输出、预期结果明确。
- 适度性：突出重点，避免冗余。
- 需求与设计分离：不写字号、颜色、图标尺寸等设计细节。

## 文档承载约定（语义 SSOT）

- API/CLI 适用性判定见标准包 `requirement-structure-single-source.md` 的“API/CLI 适用标准”。
- `README.md`：只维护导航、索引、追踪矩阵、版本入口，不承载第一章/第二章事实正文；并必须显式声明 API/CLI 适用性（不适用时写明“不适用”说明）。
- `requirement-main.md`：承载第一章产品总述与第二章入口组织结构；有 UI 时第二章包含页面组织结构。
- `requirement-[module].md` 或等价聚合详细文档：承载第三章起页面详细描述。
- `requirement-api.md`：承载服务端 API 主定义（若适用）。
- `requirement-cli-command.md`：承载 CLI Command 主定义（若适用）。
- `requirement-non-functional.md`：承载非功能主定义。

## 双时态写作口径

### 阶段写作时态（默认）

- 允许第二章入口摘要与详细页面/API/CLI 文档短期并存。
- 第二章入口简述仅为摘要级，不得定义可执行规则。

第二章禁写项统一引用标准包 `requirement-structure-single-source.md` 的“章节承载与可执行规则边界”；本文不重复维护清单。

### 完成收敛时态（发布前）

- 清理第二章中已下沉到详细文档的规则型表述。
- 第二章保留“功能概述 + 场景 + 入口关系/调用关系 + 主定义链接”；有 UI 时可包含跳转关系。
- 发现冲突时以详细文档主定义为准，第二章改为引用。

## 核心能力收敛（在第一章 1.4 之后执行）

目的：先识别“哪些行为环节最难、最关键、最需要先确认，并会在概要设计/详细设计阶段形成主要技术难点或系统复杂点”，再展开页面/API/CLI/非功能细节。

### 0.1 初版产物

- 初版位置：完成 `1.4 主要功能及核心场景` 的全量场景清单后，在第一章内完成阶段 0 初版。
- 三份产物：全量场景清单、核心能力候选池与取舍记录、正式核心能力清单。
- 字段合同、证据状态、`top_level / derived` 分层与反模式统一引用标准包 `5.2`，本文件不重复维护。

### 0.2 入选判定

- 候选成立条件、落选条件、反模式与派生核心能力成立条件统一引用标准包 `5.2`；本文只负责按该口径执行候选池记录与正式清单收敛，不重复维护判定规则。

### 0.3 校正规则

- 第二章及后续页面/API/CLI/非功能细化过程中，若新增 `REQ-UC`、改变关键行为链、发现新的系统难点或证伪已选核心能力，必须回写候选池与正式核心能力清单。
- 回写属于阶段 0 校正，不视为流程倒退；进入概要设计前必须完成最终校正。
- `source_req_refs` 只记录来源/归属，不表示核心能力与 `REQ-UC` 存在对应、覆盖或验收替代关系。

## 阶段切换与暂停

- 阶段顺序、编号与放行条件统一引用标准包 `7/8` 节，本文件不再重复维护阶段流程。
- 默认在当前阶段完成后先执行轻量自检：结构边界、编号契约、适用性声明、重复主定义、明显遗漏。
- 只有存在高风险未决项时才暂停，例如：
  - 核心能力入选/落选仍无法判断；
  - API/CLI 适用性无法从现有范围直接判定；
  - 验收口径或映射关系存在明显分叉风险。
- 若无上述高风险未决项，允许连续推进。

## 第一章：产品总述

目的：让读者快速理解产品类型、价值、目标用户和功能范围。

承载位置（默认）：`requirement-main.md`。

应输出：
- 产品用途：产品类型、市场定位、目标市场、竞品背景。
- 目标用户：用户画像、使用场景、用户需求、用户痛点。
- 用户核心痛点：可追踪到目标用户和主要场景的痛点证据，是后续核心能力候选与证据引用的重要来源。
- 主要功能及核心场景：按功能列出概述和核心使用场景。
- 核心能力定义：基于“主要功能及核心场景”提炼重点/难点行为（`P0/P1/P2` 核心能力）、业务结果、主价值链、最低验收口径，以及后续概要设计/详细设计必须展开的系统复杂点。

第一章推荐顺序（本技能）：
- `1.1 产品用途`
- `1.2 目标用户`
- `1.3 用户核心痛点`
- `1.4 主要功能及核心场景`
- `1.5 核心能力定义`
- `1.6 场景编号与入口追踪`

场景编号约束（强制）：
- 在本章首次出现核心场景时分配 `REQ-UC-XXX`。
- 同一场景在后续章节沿用同一编号，不得重排复用。
- `1.6` 在阶段 0 只记录 `REQ-UC` 与入口类型占位，可写“API 待判定 / CLI 待判定 / 无接口入口 / 无命令入口”；不得在 API/CLI 主定义完成前强行生成最终 `API-INTENT-XXX` 或 `CLI-INTENT-XXX`。
- API/CLI 主定义完成后，再回填 `1.6` 的最终接口意图追踪与编号差集结果。

## 第二章：入口组织结构（有 UI 时为页面组织结构）

目的：建立需求入口骨架，确保第一章中的实际入口都能被追踪；有 UI 时让 UI 功能和 UI 场景映射到页面或页面流程；无 UI 时明确页面组织不适用，并记录 API-only/CLI-only 入口组织关系。非 UI 场景先在 `1.6` 标记入口类型或待判定，不强制补页面，API/CLI 主定义完成后再回填最终追踪。

承载位置（默认）：`requirement-main.md`。

本章应覆盖：
- 入口分析：每个场景由 UI、API、CLI 或混合入口承接。
- UI 页面组织（若适用）：页面分类、页面关系、页面编号与命名、摘要级页面简述。
- API-only/CLI-only 入口组织（若适用）：入口类型、承接场景、主定义链接与非功能约束链接。
- 多步骤流程：流程概述、流程图、数据流转（不写规则细节）。

建议在本章维护“入口索引表”（摘要级）：

```md
| REQ-UC-ID | 场景名称 | 入口类型 | 入口摘要 | 主定义链接 |
| --- | --- | --- | --- | --- |
| REQ-UC-001 | ... | UI/API/CLI/API-only/CLI-only | ... | modules/requirement-xxx.md#... |
```

页面简述模板（摘要级，UI 适用时）：

```md
页面名称：[页面名称]
- 功能：一句话概述
- 场景：进入该页面的典型业务场景
- 页面关系：前置页面、后续页面、跳转关系
- 主定义链接：指向后续详细章节（或模块文档）
```

无 UI 入口简述模板（摘要级）：

```md
入口名称：[API-only/CLI-only 入口名称]
- 入口类型：API-only / CLI-only
- 场景：承接的 `REQ-UC-XXX`
- 主定义链接：指向 API 或 CLI 主定义文档
- 页面组织：不适用，原因：无 UI 入口
```

## 第三章起：页面详细描述

目的：让开发人员能准确理解并实现每个页面。

基本规则：
- 每个 UI 页面必须有唯一主定义位置，可承载在单页面章节、模块文档或聚合详细文档的小节中。
- 页面编号和标题与第二章入口组织结构中的页面组织严格对应。
- 页面可执行规则从本章开始定义。

## 服务端 API 定义（若适用）

目的：明确服务调用入口与数据交互契约，保障跨服务/前后端协作一致性。

进入条件：相关 UI 页面章节（若存在）已完成当前轮收敛，并满足标准包的阶段放行条件。

原则：
- 场景来源映射、业务意图回指、复用条件与拆分条件统一引用标准包 `6.1`；本节仅展示推荐记录方式。
- 契约单一来源：字段与口径只在一个主位置定义。
- `必要步骤` 的触发条件与可省略条件统一引用标准包第 `5` 章；本节不重复维护判定规则。
- 不承载 CLI 交互细节（参数解析、命令分组、终端输出样式）。

建议按标准包 `6.1` 在文档中维护映射表：

```md
| API-INTENT-ID | 接口标识 | 对应 REQ-UC-ID（至少 1 个，可多值） | 业务意图 | 主定义章节 |
| --- | --- | --- | --- | --- |
| API-INTENT-001 | POST /v1/orders | REQ-UC-001 | 创建订单 | requirement-api.md#... |
```

## CLI Command 定义（若适用）

目的：明确命令行入口的命令语义、参数契约与交互行为，保障 CLI 实现与业务场景一致。

进入条件：相关 UI 页面章节（若存在）已完成当前轮收敛，并满足标准包的阶段放行条件。

原则：
- 场景来源映射、业务意图回指、复用条件与拆分条件统一引用标准包 `6.1`；本节仅展示推荐记录方式。
- 命令契约单一来源：命令名、参数、返回码、输出语义只在 CLI 文档主定义。
- 与 API 文档解耦：CLI 与 API 作为不同入口分别维护各自主定义；不得将任一入口文档作为另一入口文档成立的唯一前提。

建议按标准包 `6.1` 在文档中维护映射表：

```md
| CLI-INTENT-ID | 命令标识 | 对应 REQ-UC-ID（至少 1 个，可多值） | 业务意图 | 主定义章节 |
| --- | --- | --- | --- | --- |
| CLI-INTENT-001 | mytool sync --all | REQ-UC-003 | 同步全量数据 | requirement-cli-command.md#... |
```

## 非功能需求

目的：补齐质量约束。

进入条件：API（若适用）与 CLI（若适用）章节已完成当前轮收敛，并满足标准包的阶段放行条件。

应覆盖：
- 性能需求、安全需求、可用性需求、兼容性需求；若某子项在本轮不适用，按标准包 `5.3` 记录非功能范围豁免，不用空章节或泛化说明替代。

## 完成收敛清单

整体复审前必须完成：
- 阶段 0 初版收敛与最终校正已完成，并满足标准包 `5.2/7.0`。
- `P0/P1` 核心能力已按标准包 `5.2` 完成证据收敛；若仅达到 `evidence_ready`，需列明进入概要设计所依赖的关键假设。
- 核心能力清单已按标准包 `5.2` 通过目标口径、分层、设计承接与反模式检查。
- 第二章仅保留摘要级入口简述与链接；有 UI 时页面简述仍只保留摘要级信息。
- 可执行规则仅存在于详细页面/API（若适用）/CLI（若适用）/非功能主定义文档。
- 版本矩阵一致、引用链可达、章节映射完整。
- 编号契约完整且稳定：`REQ-UC-XXX`、`API-INTENT-XXX`、`CLI-INTENT-XXX`（若适用）。
- `1.6` 已从阶段 0 占位更新为最终接口意图追踪；未形成接口/命令入口的场景已说明正常不映射原因。
- API/CLI 适用性结论包含判定依据：`适用/不适用 + 理由`，并引用标准包“API/CLI 适用标准”。
- 非功能需求已覆盖默认子项；若存在范围豁免，已按标准包 `5.3` 记录豁免子项、范围、原因与风险口径。
- 编号差集结果与入口分支追踪结果满足标准包第 `6` 章与 `6.1` 的完成收敛口径。
- 若存在缺失映射或真实 `UC-接口映射豁免`，已按标准包第 `6` 章与 `6.1` 回写到对应主定义位置。
