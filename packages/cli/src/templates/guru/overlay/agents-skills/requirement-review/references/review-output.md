# 审核输出模板

说明：组织结构与完成口径必须依据同级标准包 `../requirement-doc-standard/references/requirement-structure-single-source.md`（从 requirement-review Skill 目录解析）；严重度与阻断判定依据 `references/review-baseline.md`。本文仅定义审核输出格式。

输出分为“前置失败输出”和“常规门禁输出”两种。若语义 SSOT 前置不满足，必须使用前置失败输出，仅列前置缺口与修订方案，不输出 API/CLI 适用性、编号差集、核心能力结论、审核矩阵等后续逐章状态。语义 SSOT 前置通过后，常规门禁输出必须保持 Findings 在前。默认输出保持精简：Findings、必要结构概况、总结。必要结构概况只保留影响结论的字段；未命中 finding 的展开状态不要默认盘点，但非功能范围豁免必须稳定记录来源，并按标准包 `5.3` 或审核指令记录子项、范围、原因与风险口径。Finding 建议与修订方案必须按标准包第 `12` 章判定局部修订或文档级重构；本模板不复制修订形态规则。若没有任何 Findings，写“无 Findings”；若没有 P1/阻断性 P2 但存在非阻断问题，先写“无 P1/阻断性 P2 Findings”，再列出非阻断 Findings。本模板中的 `P1/P2/P3` 指审核发现严重度（`finding_severity`）；核心能力优先级应写作 `capability_priority=P0/P1/P2` 或放在明确的核心能力上下文中。

## 前置失败输出

仅当语义 SSOT 前置不满足时使用：

```md
## 前置缺口

1. 标题
- 位置：`<文件路径:行号或章节>`
- 缺口：`<为什么不满足语义 SSOT 前置>`
- 修订方案：`<按标准包第 12 章判定后的局部修订或文档级重构动作>`

## 结论

- 文档组织模式：`不满足语义 SSOT`
- 是否继续逐章门禁审核：`否`
- 下一步：`修正前置缺口后重新执行 requirement-review`
```

## 常规门禁输出

语义 SSOT 前置通过后使用：

```md
## Findings

1. [P1/P2/P3] 标题
- 位置：`<文件路径:行号或章节>`
- 问题：`<具体描述>`
- 建议：`<按标准包第 12 章判定后的局部修订或文档级重构动作>`

## 必要结构概况

- 文档组织模式：`满足语义 SSOT`
- 审核口径：`<门禁审核>`
- 文档路径：`<路径>`
- 核心能力主定义位置：`<文件路径:章节>`
- 第二章入口组织主定义位置：`<文件路径:章节；有 UI 时为页面组织结构，无 UI 时说明页面组织不适用>`
- API/CLI 适用性：`<API: 适用/不适用（理由）；CLI: 适用/不适用（理由）>`
- 入口分支追踪结论：`<UI 场景 / API-only 场景 / CLI-only 场景按标准包 6.1 的可达性；缺失或正常不适用说明>`
- 编号差集检查：`<正常不映射 / 真实 UC-接口映射豁免 / 缺失映射>`
- 非功能范围豁免：`<无 / 来源=需求文档/审核指令；需求文档内豁免需列 waived_item、scope_refs、waiver_reason、risk_statement；审核指令豁免需列子项、范围、原因与风险口径；若冲突说明以审核指令为准>`
- 核心能力相关结论（仅在影响结论或命中 finding 时输出）：`<按标准包 5.2/7.0 汇总承接、目标、反模式、confirmation_status/open_questions，并引用对应 finding>`
- 其他影响结论的状态（仅在影响结论、命中 finding 或用户要求时输出）：`<如 capability_priority=P0/P1 证据状态>`

## 总结

- 结论：`<需求文档质量评估>`
- P1 问题数：`<N>`
- P2 问题数：`<N>`
- P3 问题数：`<N>`
- 是否可进入概要设计：`<是/否，前提条件>`
- 可进入下一阶段：`<是/否，前提条件>`
```

## 可选审核矩阵

仅当语义 SSOT 前置通过，且用户明确要求矩阵，或文档复杂到必须用矩阵说明覆盖情况时输出：

```md
| 审核项 | 状态 | 备注 |
| --- | --- | --- |
| 核心能力收敛 | 已完成/部分完成/缺失 | 按标准包 `5.2/7.0`，仅摘影响结论的证据 |
| 核心能力目标一致性 | 已通过/未通过 | 按标准包 `5.2`，不展开未命中的 checklist |
| 入口组织结构 | 已覆盖/部分覆盖/缺失 | UI/API/CLI 入口覆盖；无 UI 时页面组织不适用声明 |
| 入口分支追踪 | 已覆盖/部分覆盖/缺失 | 按标准包 `6.1` 说明 UI/API-only/CLI-only 分支可达性 |
| 页面详细描述（若适用） | 已覆盖/部分覆盖/缺失/不适用 | 说明 |
| 服务端 API（若适用） | 已覆盖/部分覆盖/缺失/不适用 | 说明 |
| CLI Command（若适用） | 已覆盖/部分覆盖/缺失/不适用 | 说明 |
| 编号契约与差集 | 已覆盖/部分覆盖/缺失 | 正常不映射、真实豁免、缺失映射 |
| 非功能需求 | 已覆盖/部分覆盖/缺失/范围豁免 | 说明 |
| 重复定义处理 | 已收敛/未收敛 | 按完成收敛口径说明 |
```

## 阻断附加要求

- 若存在未解决 P1 或阻断性 P2，必须明确“不可进入下一阶段”。
- 若 API/CLI 不适用，只需说明不适用依据及其对编号追踪的影响，不要求逐个 `REQ-UC` 声明豁免。
- 若存在真实 `UC-接口映射豁免`，必须说明对应 `REQ-UC`、豁免原因与必要影响。

## 复审闭环

```text
$requirement-writing（阶段写作）
  -> 写作内置轻量自检 / 必要时阶段确认
  -> 完成收敛清理
  -> $requirement-review（门禁审核）
  -> 若存在阻断问题，回到 writing 修正；否则进入下一阶段
```
