# 需求文档审核基线

说明：文档体系定义必须以同级标准包 `../requirement-doc-standard/references/requirement-structure-single-source.md` 为单一来源（从 requirement-review Skill 目录解析）；由入口 `SKILL.md` 负责定位并读取标准包。本文聚焦审核检查矩阵与判定规则。

## 目录
- 标准结构
- 文档组织模式

## 标准结构

默认以“文档集整体结构”作为审核基线：

```text
第一章：产品总述（包含阶段 0 初版产物：1.4 主要功能及核心场景后，在 1.5 完成核心能力初版收敛；最终校正按标准包 `5.2/7.0`，从候选池、正式核心能力清单、`1.6` 最终接口意图追踪、编号差集检查结果、入口分支追踪结果，以及重复事实清理是否完成判断）
第二章：入口组织结构（有 UI 时为页面组织结构；无 UI 时说明页面组织不适用并记录 API/CLI 入口组织）
第三章起：每个页面必须有唯一主定义位置，可在单页面章节、模块文档或聚合详细文档中承载（若适用）
服务端 API 定义（若适用）
CLI Command 定义（若适用）
非功能需求（性能、安全、可用性、兼容性）
```

注：API/CLI 适用性判定见标准包 `requirement-structure-single-source.md` 的“API/CLI 适用标准”。

## 文档组织模式

- 本审核技能采用语义 SSOT 口径：README 导航，`requirement-main.md` 承载第一章/第二章入口组织主定义。
- 第三章起详细内容可采用模块化拆分或聚合详细文档。
- 若输入文档不满足语义 SSOT，必须仅输出前置缺口与整改项，不展开后续逐章门禁审核；修正后再重新执行门禁审核。
- 若项目内 API/CLI 适用性口径与标准包冲突，按标准包判定并输出整改项。

语义 SSOT 主从约束：
- README 仅维护导航、索引、追踪矩阵、版本入口。
- 第一章与第二章入口组织在 `requirement-main.md` 主定义。
- 详细页面（若适用）/API（若适用）/CLI（若适用）/非功能在子文档主定义。

样例参照：
- `../requirement-doc-standard/references/examples/unique-structure-minimal/`（从 requirement-review Skill 目录解析）

## 审核口径

- `$requirement-review` 仅用于门禁审核（需求全稿完成后）。
- 阶段写作中的中间态默认执行 writing 内置轻量自检；仅高风险歧义时才暂停做少量确认，不等同于调用本技能。

### 门禁审核

适用：整体复审、发布前、进入下一阶段。
- 强制单一来源：可执行事实不得双主定义。
- 重复定义、口径冲突与不可验收问题的严重度与阻断口径按本文“严重度规则”判定。

## 核心能力目标口径

- 核心能力目标、来源/归属、候选成立条件、`top_level / derived` 分层、字段合同、证据状态与反模式统一引用标准包 `5.2`。
- 本审核基线只检查文档是否按标准包落地，不在此重复维护难点信号或反模式清单。
- 若核心能力清单退化为场景重排、功能全量打包或普通模块拆分，按本文“严重度规则”处理。

## 各章节应覆盖的内容

### 第一章：产品总述
- 产品用途、目标用户、用户核心痛点、主要功能及核心场景。
- 主要功能及核心场景之后的阶段 0 产物：核心能力候选池、正式核心能力清单。
- 最终校正不是独立字段；按标准包 `5.2/7.0`，从候选池、正式核心能力清单、`1.6` 最终接口意图追踪、编号差集检查结果、入口分支追踪结果，以及重复事实清理是否完成判断。
- 核心能力定义：按标准包 `5.2` 核查候选池、正式核心能力清单、字段合同、优先级、证据状态、设计承接、`top_level / derived` 分层与反模式；本基线不重复维护 5.2 的判定规则。

### 第二章：入口组织结构
- 实际入口覆盖：UI、API-only、CLI-only 或混合入口。
- 有 UI 时检查 UI 功能/UI 场景到页面映射、页面分类、页面关系、页面编号与命名。
- 无 UI 时检查页面组织不适用声明，以及 API/CLI 入口组织关系和主定义链接。
- 入口简述（摘要级）。
- 多步骤流程概述与数据流转。

### 第三章起：页面详细描述
- 仅在存在 UI 入口时检查。
- 每个页面必须有唯一主定义位置，可承载在单页面章节、模块文档或聚合详细文档的小节中。
- 页面目标、业务规则、交互行为、输入输出、状态与错误语义；不检查视觉布局或组件实现细节。

### 服务端 API（若适用）
- 命名、描述、输入、输出、异常。
- 与对应场景及相关页面交互保持一致；非 UI 场景可直接由 API 主定义承接。
- 按标准包第 `5` 章核查 `必要步骤` 是否需要声明及其覆盖情况。
- 维护 `API-INTENT-XXX`。

### CLI Command（若适用）
- 命令、参数、输出语义、退出码清晰。
- 与对应需求场景保持可追踪；复用与拆分条件统一按标准包 `6.1` 判定。
- 与 API 文档解耦：两类入口分别维护各自主定义，不互为成立前提。
- 维护 `CLI-INTENT-XXX`。

### 编号契约（跨章节）
- `REQ-UC-XXX` 在需求场景主定义位置完整且稳定。
- `API-INTENT-XXX` / `CLI-INTENT-XXX` 完整且稳定（若适用）。
- 入口分支追踪、业务意图回指、复用/拆分条件、正常不映射/真实豁免/缺失映射的分类口径统一按标准包第 `6` 章与 `6.1` 判定；本基线不另起映射基数。
- 必须输出编号差集检查结果；真实 `UC-接口映射豁免` 的声明主体、原因与必要影响说明按标准包第 `6` 章核查，缺失或冲突的严重度按本文“严重度规则”判定。

### 非功能需求
- 性能、安全、可用性、兼容性。
- 若存在非功能范围豁免，按标准包 `5.3` 或审核指令核查豁免子项、适用范围、原因与风险口径；审核指令与需求文档冲突时，以审核指令为准。

## 审核步骤

### 步骤 0：识别结构与口径
- 判定文档组织模式（是否满足语义 SSOT；不满足时仅输出前置缺口与整改项，并停止后续逐章门禁审核）。
- 判定审核口径（门禁审核）。
- 判定“阶段 0 核心能力初版收敛与最终校正”是否完成，以及核心能力边界是否正确。
- 判定核心能力是否满足目标口径（重点/难点行为识别）。
- 记录第一章与第二章入口组织主定义位置。
- 建立章节映射（`REQ-UC -> 页面/API/CLI -> 非功能`，按入口类型分支；无 UI 时不强制页面分支）。

### 步骤 1：结构完整性
- 按文档集检查必要章节是否齐全。
- 按标准包“API/CLI 适用标准”先判定 API/CLI 是否适用，再检查对应文档是否应存在或不应存在。

### 步骤 2~6：分章节审核
- 产品总述、入口组织、页面详细（若适用）、API（若适用）、CLI（若适用）、非功能逐章检查。

### 步骤 7：一致性交叉检查
- 术语、状态、流程、交叉引用一致性。
- 契约单一来源与单向维护。
- 主从一致性与版本矩阵一致性。
- 核心能力与场景清单是否被错误同构。

### 步骤 8：门禁专属检查
- 确认重复主定义是否清零。
- 确认核心能力反模式是否清零。
- 若存在阻断性 P2，明确结论为“不得进入下一阶段”；非阻断 P2 需记录继续推进所依赖的明确假设。

| 审核项 | 核查重点 |
| --- | --- |
| 核心能力收敛 | 是否按标准包 `5.2/7.0` 完成阶段 0 三产物、正式核心能力清单与证据收敛 |
| 核心能力目标一致性 | 是否按标准包 `5.2` 检查重点/难点行为目标与反模式 |
| 核心能力设计承接 | 是否按标准包 `5.2` 检查概要设计/详细设计承接字段 |
| 核心能力候选池与取舍证据 | 是否按标准包 `5.2` 检查候选池、取舍记录与待定项 |
| 核心能力优先级收敛 | 是否按标准包 `5.2` 检查 `capability_priority`、优先级证据与防膨胀结果 |
| 产品总述 | 用途、用户、用户核心痛点、核心场景是否完整 |
| 入口组织结构 | UI/API/CLI 入口覆盖、编号命名、关系是否完整；无 UI 时页面组织不适用声明是否明确 |
| 页面详细描述（若适用） | 是否具备可实现、可测试信息 |
| API/CLI 适用性 | 是否按标准包统一判定，且不适用说明是否明确 |
| 服务端 API（若适用） | 用例映射、必要步骤、契约单一来源 |
| CLI Command（若适用） | 场景映射、命令契约、与 API 文档解耦 |
| 编号契约 | REQ-UC/API-INTENT/CLI-INTENT 完整稳定且双向追踪 |
| 入口分支追踪 | UI 场景、API-only 场景、CLI-only 场景是否按标准包 `6.1` 可达 |
| 非功能需求 | 覆盖或按标准包 `5.3` / 审核指令声明的豁免说明是否清晰 |
| 单向维护 | 通用规范不维护消费方清单 |
| 主从一致性 | README/requirement-main/子文档职责边界清晰 |
| 重复定义处理 | 是否满足完成收敛的单一来源要求 |

## 严重度规则

- 本节维护 `$requirement-review` 的审核发现严重度与阻断口径；标准包只定义需求文档写作合同与完成口径。
- 本节的 `P1/P2/P3` 均指审核发现严重度（`finding_severity`），不表示核心能力优先级（`capability_priority=P0/P1/P2`）。
- P1：缺失或冲突导致无法开发、无法验收、范围无法界定，或核心能力整体退化为场景重排/功能全量打包/普通模块拆分。
- P2：可继续开发，但存在高概率返工、口径分叉、设计承接不足、证据未收敛或追踪关系不完整。
- P3：表达、组织或局部可读性优化，不影响主流程实现、验收口径与设计承接。
- `capability_priority=P0/P1` 的核心能力缺少难点焦点、复杂度/风险证据、设计承接问题空间或展开粒度时，至少 P2；若导致无法判断概要设计边界或验收口径，升级为 P1。
- 核心能力优先级缺少可辩护依据时至少 P2。
- 任一可执行事实双主定义时至少 P2；若事实冲突或不可验收，升级为 P1。
- `capability_priority=P0/P1` 的核心能力仍为 `ai_drafted`，或存在会改变范围/验收口径的高风险 `open_questions`，至少 P2，且不得进入概要设计。
- P2 仅在影响范围、验收口径、设计承接或返工风险实质成立时阻断；其余可带明确假设进入下一阶段。
