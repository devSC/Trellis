# 客户端概要设计 — 单一来源规范（L1）

> 本文件是概要设计阶段的唯一权威规则。writing/review 只做编排与判定，不得复写本文规则正文。
> 上游硬输入：需求阶段产物（核心能力清单 P0/P1 + 行为规格）。
> 横向依赖：通用方法 SSOT `.trellis/spec/guides/golden-path.md`（分层依赖律）+ 目标仓库 `project-conventions.md`。

## 1. 装载与硬前置（WX/EX 共用）

执行写作或审核前必须依次确认，任一失败即终止并输出前置缺口：

- P1 本文件可读。
- P2 通用 golden-path 可读（分层依赖律是归属判定的基准）。
- P3 目标仓库 `project-conventions.md` 可读，且通过其内置校验清单 C1~C5。
- P4 需求产物可定位，且核心能力清单存在 P0/P1 条目。若需求产物缺失：仍可产出概要草稿，但必须记录**显式假设**（依据、影响范围、验证时点），且不得宣称"可进入详细设计"。

## 2. 产物合同（概要文档必含章节）

概要设计文档（建议路径：目标仓库 `docs/design/<feature>/overview.md`）必须包含：

1. **设计约束与输入**：承接的需求核心能力（逐条引用 P0/P1 编号）、技术栈约束、显式假设清单。
2. **行为集合**：行为枚举结果（见 §3）。
3. **归属判定表**：行为/状态 → owner 层 → 归属理由（见 §4）。**这是概要的核心产物。**
4. **页面流与路由**：页面间导航、入参出参、deep link（仅 UI 需求；非 UI 需求显式标注 N/A）。
5. **技术决策承接清单** `technology_decision_handoff[]`：三方 SDK 选型、平台通道、gurusdk 能力复用、缓存策略等架构显著决策——逐条：决策点 / 候选 / 选定 / 理由 / 交给详细设计展开的字段。
6. **详细设计承接索引**：`chapter_target → detail_doc_type` 映射（detail_doc_type 取值见详细设计标准包 L1 §2 的九分类）。每个归属判定表中的 owner 必须被至少一个索引条目覆盖。
7. **未决问题**：显式列出，标注风险等级。

## 3. 行为枚举方法（生成动作）

从需求行为规格出发，按以下顺序枚举行为空间，**禁止从名词/组件出发**：

1. 用户操作（点击、输入、手势、进入/离开页面）。
2. 系统反应（状态变化、数据读写、网络请求、副作用）。
3. 失败路径（网络失败、数据缺失、非法输入、权限拒绝、并发冲突）。
4. 生命周期事件（前后台切换、页面销毁、进程恢复）。

每条行为：`Given <前置> When <触发> Then <后置 + 状态变化>`，并标注涉及的状态与数据。

**编号纪律**：每条行为以 `### BHV-NNN <短名>` 标题定义（NNN 数字；创建后不复用、不重排，删除留洞）。归属表、详细设计、测试与实现切片对行为的引用一律写 `BHV-NNN` 编号 token——这是机器追溯的依据（`guru_gate.py trace-matrix` 据此生成 行为×归属×单元×测试×切片 矩阵，断链被 Gate 拦截）。归属判定表逐行以 BHV 编号开头。

## 4. 归属判定方法（核心规则）

对每条行为/每个状态，按分层依赖律判定**唯一 owner**：

| 行为/状态类型 | 归属层 | 判定理由模板 |
|--------------|--------|-------------|
| 界面结构、交互响应、design token 消费 | Page / Widget | 只承接展示与输入，不拥有规则 |
| 页面状态字段、事件分发、流订阅 | Controller | 页面生命周期内的状态容器 |
| 有状态业务流程、响应式流 | UseCase | 业务规则与状态 owner |
| 无状态工具、跨域转换 | Service | 可重用、无流 |
| 数据访问合同、缓存策略、错误转换 | Repository（必经 DataSource） | 数据一致性 owner |
| 表结构、迁移、接口合同 | DAO / API | 持久化与协议边界 |
| 三方 SDK、平台通道、iOS 交付面 | External/Platform | 外部依赖收口 |

归属判定表每行必须回答三问：**为什么属于它？为什么不属于别人？为什么需要（或不需要）独立存在？**

硬约束：
- 归属方向不得违反分层依赖律（如把数据访问归给 controller）——违反即 review 直接 fail。
- 一个状态只能有一个写 owner；其他层只能读/订阅。
- 不得在概要阶段发明 Manager/Helper/Util 等无行为来源的结构（名词先行反模式）。

## 5. 阶段边界（概要不做什么）

概要只闭合：**边界、语义、链路、取舍、索引**。以下内容禁止在概要展开，发现即属越界：

- 字段级合同、方法签名、DDL、具体 API 路径（属详细设计）。
- 代码、伪代码、文件路径级实现安排（属实现阶段）。
- 重新决定需求 scope 或私自拍板未决业务规则（回需求阶段）。

## 6. 完成判定与 Gate

概要可进入详细设计，当且仅当：

- G1 行为集合覆盖需求全部 P0/P1 核心能力（逐条可追溯）。
- G2 归属判定表完整：每条行为有唯一 owner + 三问理由；无分层依赖律违例。
- G3 涉及权限/数据采集/三方域名的行为，已在技术决策承接清单标注合规依据（最小权限、用途可解释）。
- G4 详细设计承接索引非空，且覆盖归属表全部 owner。
- G5 未决问题中无高风险项（或已获用户确认带假设进入）。

## 7. 审核基线（review 专用）

- 先证据后结论：每条 finding 必须带章节锚点或明确缺失对象。
- 严重度：P1（违反硬约束/Gate 项缺失，阻塞）；P2（归属理由不充分、索引不完整，应修）；P3（表述/一致性建议）。
- 输出互斥分支：前置（§1）失败 → 只输出前置缺口与修复动作，不展开逐章审核；前置通过 → 逐条 findings（severity/location/problem/suggestion）+ 结构概况 + "是否可进入详细设计"结论。
- 存量豁免：仅适用于实现阶段代码违例，**概要文档本身无存量豁免**——新文档必须全量符合本规范。

## 8. 修订形态判定

按 findings 修订前必须先判定：

- **局部修订**：补一条行为、补归属理由、补索引条目、改措辞 → 在原文档上改。
- **文档级重构**：归属模型错误（owner 大面积错位）、行为枚举从名词倒推、索引与归属表系统性脱节 → 重做对应章节，禁止用局部补丁掩盖错误模型。

审核发现上游缺陷（需求行为缺失/矛盾）→ 回退需求阶段修订，禁止在概要补造业务规则。
