# 复盘萃取模板（九段结构）

> Phase 3.3（spec 回写）由 `trellis-update-spec` 按本模板执行。
> 原则：**不沉淀本次需求事实，只沉淀"这类任务如何被做好"**；一次性内容不进 spec。
> 即使结论是"无可沉淀"，也要走完判断并在任务 journal 记一句原因。

## 萃取产物结构（九段，缺一不可）

按以下结构产出/更新 `.trellis/spec/` 下的方法文件（新方法建新文件；既有方法的增量直接改对应 SSOT/L2 并在文件头记修订）：

1. **名称**：kebab-case 方法名（如 `gameplay-requirement-clarification`）。
2. **适用场景**：什么样的一类任务（不是这一次需求）。
3. **输入**：执行该方法需要什么（上游产物、约定槽位、代码现状）。
4. **正向生成动作**：步骤顺序（识别 → 判定 → 展开 → 自检），动词开头。
5. **边界约束**：不做什么、不替谁决策、不进入哪个阶段的领地。
6. **输出产物合同**：产物必须包含的结构（章节/字段/表）。
7. **可验证信号**：人或脚本如何判断达标（对应 Gate/guru_gate 可检查点）。
8. **好例子 / 坏例子**：各至少一个，来自本次真实案例（脱敏业务细节，保留结构）。
9. **不适用场景**：显式列出别用它的情况。

## 判定清单（萃取前自问）

- [ ] 它适用于一类重复任务，而不是本次需求？（否 → 不沉淀，事实留在任务产物里）
- [ ] 它规定了生成顺序与判定方法？（否 → 可能只是模板/风格，写进对应 L2 的备注即可）
- [ ] 换一个相似需求还能复用？（否 → 不沉淀）
- [ ] 与既有 SSOT 冲突？（是 → 走修订形态判定：局部修订 vs 文档级重构，禁止并行两套口径）
- [ ] 属于项目级取值差异？（是 → 进 `conventions/project-conventions.md` 槽位，不进通用方法）

## 回写位置路由

| 萃取物类型 | 写到 |
|-----------|------|
| 新的一类任务方法 | `.trellis/spec/harness/<阶段域>/` 新文件 + 在 `harness/index.md` 登记 |
| 既有方法的修正/反例 | 对应 SSOT/L2 文件就地修订 |
| 生产坑（一次根因，多次可踩） | `.trellis/spec/guides/`（或迁入 big-question 域后归位） |
| 项目取值变化 | `conventions/project-conventions.md`（需 ADR 记录） |
| 存量违例修复 | 从 SLOT-15 清单移除并注明日期 |
