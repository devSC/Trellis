# 详细审核取证矩阵与严重度判级（references）

> 编排层产物：只承载取证操作与判级细则，规则正文以 L1/L2 为准；冲突时以 L1 为准。

## 1. 取证准备

- `rg -n "UNIT-|BHV-" <章节文件>` 固化编号；`rg -n "^#{1,4} " <章节文件>` 固化小节锚点。
- 概要侧基线先取证：归属表 owner 集合、承接索引目标集合、UC 承接表、技术决策清单——后续全部双向核对以此为准。
- 机器 Gate 先行：`guru_gate.py detail <task_dir>` 的结构 findings 直接并入，人工不重复机检项。

## 2. 通用检查矩阵（全部 doc_type 适用，对应 D1~D8）

| 诊断 | 取证操作 | 缺口判级 |
|------|---------|---------|
| D1 骨架 | 对照 L1 §4 模板节清单逐节打钩；N/A 节须有声明 | 缺节 P1；N/A 无声明 P2 |
| D2 八问 | 逐 UNIT 按 L1 §3 括号内可验证信号取证 | 任一问缺 P1 |
| D3 追溯 | UNIT 承接的 BHV 在 prd 存在；状态写 owner 与概要归属表行一致；依赖在概要架构图中 | 幽灵 BHV/owner 不一致 P1 |
| D4 分层 | 依赖声明对照分层律 + 命中 L2 硬规则逐条 | 违例 P1（阻断） |
| D5 粒度 | 抽查 ≥1 行为：流程详述逐步有调用对象与参数、失败分支、状态写入点 | 不达标 P1 |
| D6 测试 | 测试映射行数 ≥ 成功路径数 + 失败枚举数；测试层合理 | 高风险漏测 P1；普通漏测 P2 |
| D7 合规 | 权限/采集/PII 单元的依据；`rg -i "secret\|api_key\|token"`；制裁 TLD/私有 API/动态执行扫描 | 任一命中 P1 |
| D8 红线 | 概要外结构；未选定决策被引用；超签名级代码块（>15 行实现体视为越界信号）；错误表↔失败 BHV 对应 | 补造 P1；错误表失配 P2 |

## 3. 逐 doc_type 附加检查

### v1 类型（按 L2 逐条硬规则）

| doc_type | 附加取证 | 典型 P1 |
|----------|---------|---------|
| usecase | 状态流 owner 声明；依赖仅 repository/service 接口；usecase 间依赖有方向声明 | 注入 datasource/DAO；环依赖 |
| controller | 事件→行为映射表；三态映射；生命周期订阅/释放成对 | controller 内业务规则（重试/阈值/校验） |
| repository-datasource | 错误转换表（SLOT-04）逐枚举；缓存回落策略归属；datasource 无业务判断 | repository 绕过 datasource；datasource 含判定 |

### pending 类型（L1 八问 + 豁免核查）

- 头部 `l2_status: pending` 标注存在；design-main 有对应 `L2豁免：<doc_type> 理由：…`（full 链；无豁免 → P1）。
- page-entry：页面不拥有规则（八问 8 必含"不拥有业务判定"）；路由/Binding 为签名级。
- service：无状态无流；出现状态 → 归属错误 P1（回退概要）。
- db-dao：迁移版本号存在；DTO↔Entity 映射归属写明。
- api-network：方法签名级；错误上抛约定存在；无 Dio 实现细节。
- config-l10n：只列 key 不执行同步（出现 l10n 同步脚本调用 → P1，SLOT-07）。
- external-platform：合规面（权限用途/PrivacyInfo）逐条；凭证仅引用方式。

## 4. 跨层链路核对（directory_final 第②段 / layer_checkpoint）

| 层边界 | 核对项 | 缺口判级 |
|--------|--------|---------|
| presentation→domain | 页面/controller 只调用 usecase/service 公开行为；状态订阅有对应发射方 | 直连 data 层 P1 |
| domain→data | usecase 声明的数据依赖有承接章节；错误转换位置两侧一致 | 依赖无承接 P1 |
| data→横切 | API/DB/SDK 合同被引用方闭合；config key 有消费方 | 孤儿合同 P2 |
| 全局 | 状态写 owner 全局唯一；同一错误枚举跨章定义一致 | 多写 owner P1 |

## 5. 覆盖率核对（directory_final 第③段）

1. 概要索引目标集合 vs 现存章节文件：缺失清单（缺失只出"缺失结论+修订方案"，不进 D 诊断）。
2. UC 承接表 index_refs vs 章节：每个 UC 的链路在详细侧可走通。
3. 概要时序图参与者/调用 vs 详细行为设计：抽查 ≥1 个 UC 的时序步骤在对应章节有同名行为。

## 6. 薄文档判定（优先于逐条 finding）

满足任一即判薄文档 → 结论「不可进入」+ 文档级重构（L1 §9），不再逐条列局部 finding：

- ≥2 章骨架雷同：小节结构相同且正文为占位级（参数表空/流程详述 <3 步/测试映射 ≤1 行）。
- 全目录一次提交生成且无批内审修痕迹（chapter_status 缺失）叠加上一条任意命中。
- 逐行为设计普遍缺 mermaid 时序与异常表。

## 7. 严重度判级规则

- **P1（阻断）**：D1~D8 表中标注 P1 的项；跨层 P1 项；薄文档；章节闭合失败（机检并入）。
- **P2（应修）**：表中 P2 项；粒度局部不达标（单个行为）；孤儿合同。
- **P3（建议）**：表述/格式/术语一致性。
- 判级冲突取高；同根因合并为一条 finding 列全部位置。

## 8. 结论判定

- 任一 P1 → **不可进入**（阻塞清单 + 修订形态）。
- 仅 P2 且每条有明确修订路径 → **带明确假设可进入**。
- 无 P1/P2 → **可进入编码**。
- 结论后必须给 Gate 收口指引（用户终端 confirm detail，见 SKILL.md）。
