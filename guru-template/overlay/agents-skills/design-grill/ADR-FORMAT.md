# ADR 格式

ADR 落在目标仓库 `docs/adr/`，顺序编号：`0001-slug.md`、`0002-slug.md`。目录惰性创建，只在第一条 ADR 真正需要时建立。

## 模板

```md
# {决策的一句话标题}

{1~3 句：上下文是什么、我们决定了什么、为什么。}
```

一条 ADR 可以只有一段。价值在于记录做过一个决策以及为什么，而不是把章节填满。正文中文优先；代码标识符、库名、路径、协议字段、命令保留原文。

## 可选章节

只在确实增加价值时加入，多数 ADR 用不上：

- **Status** frontmatter：`proposed | accepted | deprecated | superseded by ADR-NNNN`。
- **Considered Options**：只在被否决的备选值得未来读者记住时写。
- **Consequences**：只在下游影响不显然、需要点名时写。

## 编号

扫描 `docs/adr/` 取现存最高编号 +1，不跳号、不复用。

## 何时提议 ADR

三条全中才提：

1. **难以回头**：以后改主意的代价不小。
2. **缺上下文会困惑**：未来读者看代码或文档会问"为什么这样做？"。
3. **真实权衡的产物**：确实存在可选方案，并且选择有具体理由。

易回退、不令人意外、没有真实备选的决定不记 ADR。

## 常见合格类型

- 架构形态、分层边界、上下文边界或数据所有权边界。
- 关键技术栈或运行时方案切换。
- 跨系统、跨服务、跨平台或跨模块契约形态。
- 鉴权、会话、密钥引用、隐私、合规或外部政策驱动的技术选择。
- 明确拒绝一种未来很可能再次被提出的方案。
- 代码里看不出来但会长期约束实现的外部要求。

不够格的决定按 golden-path / project-conventions 正常执行即可，不写 ADR。
