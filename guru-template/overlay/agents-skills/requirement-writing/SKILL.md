# Requirement Writing

## 目标

- 输出完整、清晰、一致、可测试的产品需求文档。
- 在需求阶段优先识别“决定系统成败的重点/难点行为”，而非重列场景清单。
- 明确区分“全量功能/场景清单（追求覆盖）”与“核心能力清单（追求关键性）”。
- 坚持需求与设计分离，只写功能和业务要求，不写视觉样式和实现细节。
- 允许“先粗后细”的分阶段展开，同时保证在完成收敛前完成单一来源收敛。

## 最小输入与自动补全

- 接受产品目标、核心功能、已有草稿、需求目录或单个文档路径。
- 信息不足时，先收敛到最小可写范围，不擅自补齐高风险业务规则。
- 若仓库中已有历史版本或同类需求，先复用命名、章节和术语约定。
- 编写阶段必须满足语义 SSOT 的承载边界：`README.md` 仅维护导航/索引/追踪矩阵/版本入口，`requirement-main.md` 承载第一章与第二章入口组织主定义；第三章起可按模块拆分或聚合成一个详细文档；接口类文档按类型拆分为 `requirement-api.md`（若适用）与 `requirement-cli-command.md`（若适用）；可执行事实的单一来源收敛在完成收敛时态强制完成。

## 核心能力口径

- 核心能力定义、候选成立条件、`top_level / derived` 分层、字段合同、证据状态与反模式，唯一引用标准包 `5.2`；本技能不重复定义。
- 本技能负责按标准包 `7.0` 执行阶段 0：在 `1.4` 全量场景清单后做核心能力初版收敛；后续详细章节若新增或改变关键 `REQ-UC`，必须回写候选池与正式核心能力清单；进入概要设计前完成最终校正。
- 写作时按标准包 `5.2` 避免核心能力反模式，不在本技能重复维护反模式清单。

## 双时态机制

### 1) 阶段写作时态（默认）

- 目标：支持“从顶至下、由粗到细”的迭代撰写。
- 允许：第二章入口摘要与后续详细页面/API/CLI 文档短期并存。
- 约束：第二章只允许摘要级描述，不得承载可执行规则主定义。

### 2) 完成收敛时态（发布前必做）

- 触发：用户要求“整体复审/进入开发/进入设计/完成收敛”，或文档准备进入正式评审发布。
- 要求：同一事实只保留一个主定义位置；第二章保留摘要与链接，不保留可执行规则。
- 输出：必须给出“重复事实清理结果”“非功能范围豁免清单”与“剩余风险”。

## 执行规则

1. 必须先读取同级标准包主定义 `../requirement-doc-standard/references/requirement-structure-single-source.md`（从本 Skill 目录解析），确认语义 SSOT 与完成口径；若该文件不可用，终止并提示先安装 `requirement-doc-standard`。
2. 再读取 `references/chapter-guide.md`，按固定阶段推进。
3. 阶段顺序、阶段 0 的时间位置与放行条件统一引用标准包 `7/8` 节；本技能不另起阶段编号或顺序。
4. 核心能力边界、候选入选、分层与反模式统一引用标准包 `5.2`；本技能不另起定义。
5. 阶段 0 初版与最终校正必须同时满足标准包 `5.2/7.0` 的三部分要求：全量场景清单、候选池与取舍记录、正式核心能力清单。
6. `核心能力定义` 的字段合同、候选池记录要求与证据收敛状态一律复用标准包 `5.2`，本技能不另起 schema。
7. 阶段切换前默认先执行本技能内置轻量自检：结构边界、编号契约、API/CLI 适用性、阶段 0 初版/校正状态、明显重复主定义。
8. 仅当存在高风险未决项时才暂停，并按 one-question loop 向用户提出 1 个最高优先级关键问题，包含决策点、影响、推荐答案和取舍；用户答复后先回写需求包 / `prd.md`，再继续下一个问题。只有用户当前消息明确要求“批量确认”“一次性确认”“这几个都按推荐处理”等覆盖多个 OQ / decision id 时，才可一次列出 2~4 个问题并逐项记录确认；模糊“继续”“好”“按推荐”不得推断为批量确认，必须回退为单个 `next_question`。
9. 若不存在高风险未决项，允许连续推进到下一阶段，不机械逐阶段等待确认。
10. 若 `P0/P1` 核心能力仍为 `ai_drafted` 或存在高风险 `open_questions`，可以继续完善需求草稿，但不得宣称“可进入概要设计”；若已达到 `evidence_ready` 且无高风险待确认问题，可带明确假设进入概要设计。本技能可草拟核心能力与整理确认问题，但不得替用户写入 `user_confirmed` 或 `user_confirmed_with_edits`。
11. 写入 `Brainstorm Evidence` 时，必须二选一留下可审计证据：
   - `Question Loop Log` 表格，列为 `oq_id | asked_at | question | recommended_answer | tradeoff | user_quote | resolved_decision | artifact_update`。
   - `Question Policy`，写 `question_policy: evidence_only` 或 `question_policy: mixed`，并列明哪些问题由仓库证据回答、哪些问题由用户当前轮确认回答。
12. `evidence_only` 只能产出 `evidence_ready` 或 `confirmed_ref`，不得写 `user_confirmed*`、`current-turn-confirmation` 或把原始 bug/source quote 当作 `user_quote`；`mixed` 必须明确区分 `source_quote`、`confirmed_ref`、`current_turn_confirmation` 和 `user_quote`。
13. 按语义 SSOT 编写：第一章与第二章入口组织写入 `requirement-main.md`；`README.md` 仅保留导航与矩阵，不复制事实正文，并显式声明 API/CLI 适用性（不适用时写明“不适用”说明）。
14. 第一章推荐章节顺序：`1.1 产品用途` -> `1.2 目标用户` -> `1.3 用户核心痛点` -> `1.4 主要功能及核心场景` -> `1.5 核心能力定义` -> `1.6 场景编号与入口追踪`；`1.6` 在阶段 0 只允许记录 `REQ-UC` 与入口类型占位，API/CLI 主定义完成后再回填最终意图追踪。
15. 第二章入口组织结构必须覆盖第一章中的实际入口：有 UI 时覆盖全部 UI 功能和 UI 场景；无 UI 时明确页面组织不适用，并记录 API-only/CLI-only 入口组织关系。若页面涉及已收敛 `P0/P1` 核心能力，可标注相关核心能力用于提醒后续设计关注，但不建立页面与核心能力的承接或覆盖关系；非 UI 场景可在 `1.6` 中先标记入口类型或待判定，API/CLI 主定义完成后再回填最终追踪。
16. 第二章入口简述只写摘要信息（功能/场景/入口关系/依赖），不写可执行细则（状态机、校验规则、守恒公式、错误码语义、强约束语义）。
17. 页面详细（若适用）、API（若适用）、CLI（若适用）、非功能为可执行规则主定义承载区。
18. API/CLI 适用性按标准包 `requirement-structure-single-source.md` 的“API/CLI 适用标准”判定；结论必须包含“适用/不适用 + 判定依据（引用标准包口径）”。
19. API/CLI 业务意图与 `REQ-UC` 的映射基数、允许复用的条件与拆分标准统一引用标准包 `6.1`；本技能不另起“一一对应”口径。
20. 采用“单一来源 + 单向维护”原则：同一事实只在一个主文档/主章节定义；其他文档仅引用，不重复定义。
21. 通用规范文档只定义“规则与适用条件”，不维护消费方清单；消费方文档必须显式声明“遵循某规范”并引用主定义位置。
22. 文档变更后必须执行一致性校验：版本矩阵、跨文档引用链、章节映射（`REQ-UC -> 页面/API/CLI -> 非功能`，按入口类型分支）三项全部对齐。
23. API（若适用）中的 `必要步骤` 定义范围、触发条件与可省略条件统一引用标准包第 `5` 章；本技能不另起判定规则。
24. 非功能范围豁免的文档内记录字段统一引用标准包 `5.3`；本技能只负责按该口径写入豁免子项、范围、原因与风险口径。
25. 进入完成收敛时态后，若仍存在重复主定义，不得给出“可进入下一阶段”结论。
26. 需求场景与 API/CLI 业务意图的编号稳定性、回指要求、映射基数、差集分类和真实 `UC-接口映射豁免` 声明主体统一引用标准包第 `6` 章与 `6.1`；本技能不重复定义。
27. 完成收敛前必须按标准包第 `6` 章与 `6.1` 输出编号差集检查结果与入口分支追踪结果，并将缺失映射或真实豁免回写到对应主定义位置。
28. 撰写、自检或按 Findings 修订需求文档时，必须按标准包第 `12` 章先判定缺陷属于局部产物缺口还是需求文档结构/语义模型缺陷，再选择局部修订或文档级重构；本技能不另起修订形态标准。

## 阶段执行约定

- 准备步骤、阶段编号、阶段顺序与放行条件统一引用标准包 `7/8` 节，本技能不再重复定义。
- 本技能只负责按标准包顺序执行，并在每次阶段切换前完成轻量自检或必要确认。

## 输出要求

- 普通写作轮次先给当前阶段正文，再给必要待确认点；无高风险未决项时不输出审核式长清单。
- 使用可追踪的章节编号和稳定命名。
- 若用户要求一次性生成全稿，仍按标准包阶段顺序组织内容，但不机械逐阶段等待确认。
- 阶段切换时输出轻量自检摘要，限于：当前时态、阶段 0 初版/校正状态、API/CLI 适用性、编号追踪状态、明显重复主定义、高风险未决项。
- 完成收敛时额外输出：重复事实清理结果、编号差集检查结果、真实 `UC-接口映射豁免` 清单、非功能范围豁免清单、剩余风险。

## 命令建议

- 用 `rg` 搜索历史需求、入口名、页面名（若适用）、API/CLI 名、命令名、模块名和术语。
- 用 `rg --files` 定位已有需求目录、模板目录和版本目录。
- 需要流程图时，优先使用 Mermaid。
